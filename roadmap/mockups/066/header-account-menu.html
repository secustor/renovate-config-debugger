Account menu in the header corner

Today the GitHub sign-in widget lives in the config toolbar — a row below the editor card, between the file-name select and the Run button. That is not where anyone looks for it: the account control belongs in the top-right corner, and its three actions (sign out, revoke, manage repository access) belong behind one menu instead of scattered as a chip, a link and a hint. The variants below are all click-to-open — try them.

All colours are var() tokens copied verbatim from index.css; the markup mirrors the class names an implementation would use. Toggle your OS light/dark theme — every state below is themed.

What's wrong.
  • Wrong corner. Every user arrives expecting the account control top-right; here it is mid-page, in a row otherwise about running the config.
  • Three controls, one concept. "Sign out" (button) and "revoke" (lowercase link) sit inside the identity chip; "Manage repository access" lives somewhere else entirely, in GithubAuthHint, only visible after a failure.
  • The copy already lies. AdvancedZone.tsx:256 tells the user that signing in is "at the top of the page". It isn't — yet.
  • It competes with Run. The signed-out state is a full-width btn reading "Sign in with GitHub", parked two controls away from the primary action.

1 — What the convention actually is

The pattern is settled enough that deviating costs discoverability, so the variants below all obey it:

  • Avatar in the top-right corner is the trigger; it is the account's own affordance, so it needs no "Account" label.
  • The panel is right-anchored to the trigger, never centred — otherwise it overflows the viewport edge in a top bar.
  • Identity (avatar + handle) is repeated as a non-interactive label at the top of the panel, so the user can confirm which account before acting.
  • The sign-out row is separated by a divider and visually distinct — it is the one destructive item.
  • Semantics are aria-haspopup="menu" / role="menu" / role="menuitem", not a listbox — screen readers must announce actions, not options.
  • The panel scales from its top-right origin, which reads as "grew out of the avatar".

The other three states

The corner has to render four ways. Ordered by how often a user sees them.

signed out v44.7.4

Labelled, not an icon: this is the discovery point for private presets. "Sign in", not "Sign in with GitHub" — the mark carries the provider.

restoring (065) v44.7.4

065's silent cookie refresh runs on mount. Without this state the corner renders "Sign in", then swaps to an avatar a beat later — a flash that reads as a bug. Gate on the cookieSession marker, which is already in localStorage and synchronous.

oauth unconfigured (043) v44.7.4

A self-hosted deployment without __RCD_OAUTH__ renders nothing at all — no disabled control, no placeholder. Unchanged from today.

4 — Variant C — one session menu, corner collapsed recommended

If the corner is the "about this session" corner (037), the account is not a separate concept — fold the theme switch and the project links in too, leaving a single trigger. The trigger's icon carries the state: an avatar when signed in, a gear when not. That one substitution is what makes the variant work — without it the signed-out and self-hosted corners are a nameless button, which was the original objection to C. A gear says "settings live here" in every deployment, including the one where sign-in doesn't exist at all.

What the gear buys. One trigger, one width, three states, and the whole .app-header-tools row reduced to a badge and a 40px button — the wrap-point problem 055 spent a doc reasoning about simply stops existing. The 065 restoring state also gets easier: the gear is the resting state, so a session that restores swaps gear → avatar with nothing reflowing, and the skeleton from variant A is no longer needed.
Two costs remain, and they are real.
  • Theme goes from one click to two. 037 chose a visible segmented control deliberately. The counter-argument: theme is set roughly once per user per machine, and it is spending ~150px of permanent header width to save one click on a decision nobody revisits. Keeping the .seg intact inside the menu means the choice is still one click once open, not a submenu.
  • Signed-out sign-in is no longer a visible button. This is the one that needs a judgement call — see below.
Is burying sign-in acceptable? Probably yes, because the header was never the real discovery path. GithubAuthHint and AuthFailureBanner already surface a labelled "Sign in with GitHub" at the moment it matters — when a private preset 404s or the rate limit bites — and 009 called those error paths "the core UX of the feature". A permanent header button is convenience for the user who already knows they need it; that user will find a gear. If this reasoning doesn't hold, the fallback is hybrid: gear-menu for everything, plus a labelled Sign in button beside it that exists only in the signed-out state and disappears once signed in.

5 — Menu anatomy & behaviour spec

What the implementation has to get right, independent of which variant wins.

Row Action Notes
Identity label none — not focusable Avatar 32px + authUser.login + "Signed in with GitHub". Falls back to a person glyph when avatarUrl is absent or fails the http(s) check (030).
Manage repository access installUrl(), new tab Currently reachable only from GithubAuthHint after a failure. Promoting it here does not remove it there — the hint is contextual, the menu is permanent.
Revoke access on GitHub REVOKE_URL, new tab Caption states the difference from sign-out. External-link glyph on the right.
Sign out onSignOut() → signOut() --error text, own group. Closes the menu, returns focus to the trigger, keeps the current result on screen.

Interaction

  • Open: click, Enter/Space. Hover must not open it — the glossary hover-card pattern is wrong for a destructive menu.
  • Close: Esc, outside click, scroll of the page, choosing any item, or the tab losing focus. Focus returns to the trigger — the same contract use-repo-load.ts:169-196 already implements for the repo form.
  • Keyboard: ↑/↓ move between menuitems, Home/End jump, typing a letter jumps to the matching row.
  • Positioning: position: absolute; right: 0 off the trigger is enough here — the trigger is always near the viewport's right edge, so the panel never needs the viewport-flipping anchoredCardStyle machinery, and staying out of a portal keeps focus management trivial.
  • Below ~380px: max-width: calc(100vw - 2rem) plus the right anchor keeps it on screen; no bottom sheet needed at this app's density.

Code shape

  • New components/AccountMenu.tsx + hooks/use-account-menu.ts (open state, outside-click, Esc, focus return) — the hook keeps AccountMenu under the jsx-max-depth: 3 ceiling, and the identity block and item list want to be their own small components anyway.
  • AppHeaderTools grows from 1 prop to 6: oauthConfigured, signedIn, authUser, restoring, onSignIn, onSignOut. All already exist in App.tsx.
  • ConfigToolbar loses five props and the whole gh-auth-chip block; ConfigColumn stops threading them. Net prop count across the three files goes down.
  • .gh-auth-chip, .gh-auth-avatar, .gh-auth-login, .gh-auth-signout, .gh-auth-revoke are then dead CSS — delete them. .gh-auth-hint and .gh-inline-signin stay (error paths).
  • AdvancedZone.tsx:256's "top of the page" sentence becomes accurate; no edit needed.
  • Nothing here touches platform/oauth.ts — the token lifecycle, 065 cookie restore and signOut() are unchanged. This is presentation only.
  • Variant C only: ThemeSwitch and ProjectLinks move inside the menu unchanged — both are self-contained and take no props, so this is a relocation, not a rewrite. AppHeaderTools then renders exactly two children, and the .app-header-tools flex-wrap rule becomes vestigial.
  • Variant C only: the trigger needs a restoring input no longer — it renders the gear until signedIn flips, so the skeleton state and its cookieSession gate can be dropped from the prop list.

Trigger state table (variant C)

State Icon Accessible name Menu contents
Signed in Avatar (or person glyph if avatarUrl is missing/rejected) "Account: octocat" Identity · Manage repository access · Revoke · Sign out · Theme · Links
Signed out, OAuth configured Gear "Settings and sign-in" Sign in with GitHub · Theme · Links
OAuth unconfigured (043) Gear "Settings" Theme · Links
Restoring (065) Gear "Settings" Same as signed-out — the gear is the resting state, so no skeleton and no reflow when the refresh lands.

The icon swap is the only thing that changes size-wise: both glyphs render into the same 26px circle, so the header's intrinsic width is constant across every state and every deployment.

Recommendation: variant C with the gear. The gear substitution turns C from the most radical option into the most coherent one — it is the only variant where the corner is a single control with a stable width in all four states and both deployment shapes, and it retires the 055 wrap-point problem rather than adding to it. Accept it if you agree that the contextual GithubAuthHint carries sign-in discovery (it fires exactly when sign-in matters); if not, take the hybrid in the note above — C's gear menu plus a signed-out-only labelled Sign in button.

Variant A remains the safe fallback: strictly fewer moving parts, no regression on any existing one-click affordance, and B is a one-line change from it (.labelled + the handle span). Note that A and C share the entire menu implementation — picking C is not more work than A, it is the same component with two extra groups and a state-dependent trigger icon.
