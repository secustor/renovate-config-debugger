Showing the resolved config without internal presets

Three ways to surface a “resolved config, internal presets kept as extends” output in the Effective Config card — starting with the proposed checkbox, then two alternatives. Amber dots flag problems, green dots mark what a variant gets right.

Verdict: a checkbox is the wrong control here.

The existing checkboxes (only overridden, show default-only) filter rows of the same document. This option produces a different document — a second merge pass that stops at internal presets — in a different rendering (plain JSON instead of provenance rows). That is a view mode, not a filter. Variant B makes the mode explicit; Variant C does it with zero new chrome if preview isn’t needed.

Variant A — checkbox in the filter bar as proposed

The new option dropped next to the existing row filters.

  1. 1The label bundles two axes into one boolean — “shallow” and “without internal presets”. What does unchecking half of that mean? A checkbox can’t answer.
  2. 2Checkboxes in this bar promise composition: they filter rows of the same list. Combine this one with only overridden and the state is incoherent — the override chains reference preset layers that no longer exist in the shallow document.
  3. 3Negative phrasing (“without …”) means checked = absence, and the 6-word label wraps the bar on mobile. Checkbox labels should name a positive, single thing.
  4. 4Ticking it silently swaps provenance rows for plain JSON — the filter input, layer select and both other checkboxes stop applying but stay enabled. Half the card’s UI becomes a lie.

Need the config before preset resolution? That document already exists: Rewrites → Copy migrated config.
  1. 1The one honest cost: a second control surface in the title bar. It earns its place by telling the truth — the whole panel changes, and the control that changes it says so.
  2. 2Row filters render only in the “By key” view, so no combination of controls can produce a state the UI can’t honour.
  3. 3“Expand presets” names the axis by outcome, with exactly two values. No “as written” option — that document (migrated, extends intact) is already copyable from the Rewrites tab, so this view starts where Rewrites stops. And no “shallow” — that word already means shallow-merge in the override chains.
  4. 4This view’s job is producing an artifact you paste into renovate.json, so Copy (and later Download) belongs here — the provenance view never needed it.

How this fits the copies that already exist

Each copyable document is one stage of the pipeline the app already teaches, owned by the tab that explains that stage. Variant B doesn’t duplicate the Rewrites copy — it continues the progression where Rewrites stops. The tab boundary is preset resolution.

  2. ·Same pattern, per tab: Rewrites’ copy sits in its step-through chrome; B’s copy sits in the JSON view’s options row. Each tab exports the document it explains — no global “export” concept to invent.
  3. ·One naming debt: “Copy migrated config” vs “Copy JSON” should share a vocabulary once both exist — e.g. both name their document: “Copy migrated config” / “Copy resolved config”. Worth aligning in the same PR.

Variant C — export menu, zero new chrome lighter alternative

The provenance view stays exactly as it is; the outputs become a quiet “Copy as…” action in the title bar, following the editor card’s title-action pattern.

  1. 1Nothing new to learn and no mode state to reset per run — but the output isn’t previewable before copying. Fine for the power user consolidating a config; weaker for the learning persona this app optimises for.
  2. 2Menus invite scope creep (markdown export, download, share…). If that list is wanted anyway, C composes with B: the menu becomes the Copy button’s dropdown inside B’s JSON view.

Engine note: “keep internal presets” is not a filter over the existing trace — it needs a second resolution pass that stops descending at presetSource === "internal" nodes and merges only the fetched layers over the repo config. That’s also why the provenance chips can’t annotate this document: its layer set differs from the traced one. Cheap to compute (the preset tree is already resolved), but it is a new engine output, which is the underlying reason it deserves a mode, not a checkbox.
