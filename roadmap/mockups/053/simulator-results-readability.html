Mockup 053 — Simulator results readability

047 staged the simulator into ask / answer / evidence, and it worked — the verdict is never buried. The remaining problem is inside the evidence: opening both drawers rebuilds the pre-047 wall, the same three facts (the changed settings) repeat at three grains (ledger, per-rule "applied" lists, step diffs), and the step diff renders the whole 10,698-line config to show three changed keys. This mock keeps 047's layers and proposes three different architectures for the evidence itself. Research notes at the bottom; full report in roadmap/2026-08-simulator-readability-research.md.

  • The same three facts render at three grains. groupName appears in the ledger, in rule 458's "applied" list, and twice in the step diff — the reader cannot tell whether scrolling reveals new information or the same fact again, so they read all of it.
  • The diff is the whole config. Three changed keys inside 10,698 lines; the line-number gutter (79 … 10696) is visually louder than the change itself. Prev/Next/Jump controls exist to survive the layout, not to serve a task.
  • Open evidence rebuilds the wall. Both drawers open is ~2,000 px of equal-weight monospace; the verdict card and the raw trace compete at the same typographic rank.
  • "3 of 719" is said four times — card title, verdict footer, drawer summary, filter row — and each repeat costs a line of reading.
  • Four vocabularies per row. A ledger row mixes code, prose, a provenance chip, and a step link inline at equal weight; nothing tells the eye what is skippable.

1 · Variant A — the ledger is the trace

DevTools' Computed-pane model: the winning value per key is the index, and expanding a key reveals that key's causal thread — the rule that wrote it (with its clause evidence inline), the value it overrode (struck through), and a jump into the replay. The rules and merge drawers demote to one quiet "full trace" line for audit-style questions. Slices the data by outcome instead of by mechanism, so each fact has exactly one home.

2 · Variant B — inspector: index left, one detail at a time

The Compiler-Explorer / Jaeger model: a persistent index rail (matched rules grouped by consequence, then the replay stops) beside a single detail pane. Selecting anything swaps the pane — the page height is constant no matter how much the user investigates. The rail pre-filters to the decisive subset: rules that changed something, rules that matched but changed nothing, and one counted row for the 716 that did not match.

3 · Variant C — one lens at a time + the digest diff

4 · Shared fixes — worth shipping under any variant

  • Digest diff. The step diff defaults to changed keys only (~ / + / −, old → new inline) with # N unchanged lines hidden — show; the full unified/side-by-side diff stays one click away. (Terraform's battle-tested shape for exactly this data.)
  • Say "3 of 719" once. The verdict owns the count; drawers/lenses/rails reference it without restating it.
  • Demote chips in evidence. Full provenance chips stay on the verdict card; inside evidence layers the same fact is a colored dot with the chip on hover — all three matched rules sharing one source was worth 3 chips × 28 characters in the screenshot.
  • Name the inert state. "Matched but changed nothing" (rule [0], ±0) is today only visible as a timeline delta; every variant above labels it, because an unexplained matched-rule-with-no-effect reads as a bug.

The variants compose: C's digest diff and elision rows are prerequisites for A and B anyway (shared fixes above), and A's threads could later sit on top of either. A plausible sequencing is C-then-A (ship the cheap structural fix, then grow the ledger into the primary trace) with B reserved for a future "audit mode" if the 719-rule population demands it.

Research notes (condensed)

  • Two views, two questions. DevTools separates "what is the value" (Computed pane: winner only, expandable to the ordered cascade with losers struck through and jump-links to source) from "why" (Styles pane) — users default to the cheap answer and escalate on surprise. Variant A is this transplanted to a sequential last-writer-wins merge. developer.chrome.com/docs/devtools/css
  • Decisive subset, never a dump. IAM policy simulator, GCP Policy Troubleshooter, Skyhigh rule tracing and LaunchDarkly evaluation reasons all pre-compute which rules were causally relevant (typed reason codes, decisive-statement labels, three visual states for matched / evaluated-unmatched / skipped) — the viewer never infers relevance from a flat list. Variant B's rail grouping and the "matched but changed nothing" badge. docs.aws.amazon.com · cloud.google.com/policy-intelligence · launchdarkly.com/docs
  • Severity-driven expansion. GitHub Actions / Buildkite auto-expand only failed steps; default disclosure state derives from "is this abnormal", never from position. Variant C pre-expands the 3 matched rules and collapses the 716 no-matches to a counted row. docs.github.com · buildkite.com/docs
  • Elided-but-acknowledged. Terraform's # (12 unchanged attributes hidden) — collapse must render as a counted placeholder, or trust dies; and false-positive "changes" (plan noise) destroy diff scannability, so the digest must be precise about what genuinely changed. The digest diff everywhere above. developer.hashicorp.com/terraform
  • Sequence ⇒ index + one detail pane. Jaeger keeps the waterfall persistent as a spatial index with a single drill-down panel beside it; Compiler Explorer keeps the floor at two panes and makes depth opt-in with the whole layout in the URL — matching the app's fragment-only share convention. jaegertracing.io · github.com/compiler-explorer
  • Constraints carried over from 047's research: never gate the verdict; two disclosure levels max; every collapsed header keeps a computed count/preview; and the per-clause predicate-vs-evaluated evidence stays one interaction away — the persona study called it "the single most convincing screen". roadmap/2026-07-progressive-disclosure-research.md · roadmap/2026-07-persona-ux-study.md
