Editor column polish

1 · The config editor must follow the theme switcher

Root cause, not a mock decision: ConfigEditor.tsx asks matchMedia("(prefers-color-scheme: dark)") — the OS — once per render. The 037 switcher deliberately overrides the OS via color-scheme, and the editor never hears about it (it doesn't even react to OS changes). Fix: derive the editor's theme prop from the app's effective scheme — the 037 stored override when set, the OS otherwise — through a small subscribed hook (useEffectiveScheme()), so the editor repaints the moment either one changes.

2 · One base Button, three variants, one height

036 unified the chrome rows, but the toolbar tier still towers over them — five button dialects remain. Proposed: every button derives from one .btn base (the 036 control metrics: 0.8rem, 0.25×0.6 padding) with exactly three variants — primary (accent fill; only Run), secondary (bordered, default text), quiet (muted text; segmented controls, footer buttons). The file <select> and inputs adopt the same metrics so a row is one height end to end. <CopyButton> and .seg keep their look — they simply re-base onto .btn.

3 · Remove the undo/redo hint

The Cmd+Z to undo, Shift+Cmd+Z to redo. line under the editor goes. Undo/redo is universal editor behavior, not app knowledge — the hint spends a permanent line of the column's scarcest resource on the least surprising fact in the UI. Nothing replaces it.

Option C — toolbar button + anchored popover

zero standing cost, but a floating surface
  • Groups the load action with the other config-level actions in the toolbar.
  • But: a popover needs its own dismiss/focus/overflow management (the 025 hover-card lesson), and it floats over the editor it's about to change instead of being part of it.

All three restore the welcome/editor/run stack to the top of the viewport; B and C free the full ~64px. Recommendation: B — it needs no floating surface, reuses the 036 chrome-row grammar, and puts the control on the card whose content it replaces.
