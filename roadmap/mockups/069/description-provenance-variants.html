Renovate Config Debugger · design exploration

Where did this description come from? — four presentation variants

Preset authors write description strings to explain what their rules do. Renovate concatenates them all into one flat array — losing the connection to the preset that wrote each one. The trace already captures enough to restore it. All mockups below use the real output of {"extends": ["config:best-practices", ":dependencyDashboard", "group:monorepos"]}: 24 accumulated strings, including two duplicates.

What the investigation established

Mechanics: description is an ordinary mergeable array option. Each preset resolves depth-first, children's strings land first, the node's own string last; strings are never deduplicated. Wrapper presets ({description, extends}) get theirs silently dropped.
Data availability: every preset-tree node already carries its own literal body (input) and its fully-merged result (resolved). Per-string attribution is a recursive positional walk — same technique as the existing computeRuleProvenance. No new trace collection needed.
Today's UI: descriptions are actively filtered out — META_KEYS excludes them from "sets real options", and the provenance view attributes the whole array to top-level extends entries only. packageRules[n].description never surfaces at all.
Prior art: GitHub blame (group consecutive same-source entries), DevTools cascade (show suppressed values struck-through, not hidden), ESLint config-inspector (merged ⇄ per-source toggle), Nix (source vs. import-path split). Renovate upstream punted on exactly this feature (discussion #38024).

Variant A · Effective Config tab

The blame ledger

The existing description row in Effective config → By key stops being a truncated wall of text. Expanding it shows every string in final array order, blame-style: each entry carries a preset chip (click → selects the node in the preset tree), consecutive entries from the same top-level extend are grouped under a hairline, and duplicates are struck through with an explanation instead of silently kept.

Variant B · Overview tab

"What this config does" — descriptions as the config's own documentation

Reframe: the accumulated descriptions are the author-written summary of the config's behavior — the same list Renovate itself pastes into onboarding PRs. A new Overview card presents them as a readable digest, grouped by the top-level extends entry that pulled each one in, deduplicated (with a count), each line attributed to its leaf preset via a quiet mono label. User-written packageRules descriptions join at the bottom — surfacing for the first time.

Variant C · Presets tab

Descriptions live in the tree

Attribution by placement instead of by label: each node in the Preset Resolution Tree shows its own description as a quote line beneath its name — the text appears exactly where it was written, so no chips are needed. Nodes whose description was silently dropped by Renovate (wrapper presets, the ignoreDeps quirk) say so, making the two invisible drop rules visible for the first time.

Variant D · everywhere descriptions appear

Attribution at point of contact — hover cards & simulator verdicts

No new panel at all. Wherever a description string is already visible — the resolved JSON document, a preset body, a simulator verdict — it becomes an attributed object: hovering any string pops the app's standard hover card naming the contributing preset, its import path, and its array position. In the simulator, a matched rule's author description is promoted to the verdict itself: the rule explains why it exists.

Synthesis

Comparison & recommendation

Variant Question it answers Where Build cost Discoverability
A · Blame ledger "Who wrote string #N, and why is it duplicated?" Effective config → By key Medium — new attribution walk + one expanded-row renderer Medium (behind expand)
B · Behavior digest "What does this config actually do?" Overview (new card) Medium — walk + grouping/dedup High (front page)
C · Tree inline "What does this preset say about itself?" Preset tree (toggle) Low — data already per-node Medium
D · Point of contact "Why does this string / this rule exist?" JSON views + simulator Low–medium — composes existing hover & chip primitives Low (hover) / High (simulator)

Recommendation: the variants share one engine primitive — the recursive per-string attribution walk — and are otherwise independent surfaces. Build the walk once, then ship B as the flagship (largest user value: it converts author intent into the config's own documentation and exposes redundant extends), with A as its "show raw order" escape hatch in the Effective Config row. C's quote-lines and D's simulator verdicts are cheap follow-ups on the same data; D's hover card falls out of the chip wiring A introduces.

Every element above reuses existing app primitives: ProvenanceChip (purple = preset, blue = repo config), the .kv ledger grid, the option-card hover, and the seg control — no new visual vocabulary required.
